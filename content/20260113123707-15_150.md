## 1/13 {#1-13}


### Course Philosophy {#course-philosophy}

Computation is Functional.
Programming is an explanatory linguistic process.
Functions map values to values. Types constrain what we can do and make it easier to prove that we've done things correctly.


### Imperative vs. Functional {#imperative-vs-dot-functional}

Imperative is like a command, functional is more expressive
Command -&gt; x := 5 (executed, has an effect)
Expression -&gt; 3 + 4 (evaluated, no effect)


### Parallelism {#parallelism}

Work vs. Span
Work is the total sequential time; number of operations.
Span is parallel computation. How long woudld it take if one could have as many processors as one wants.

### Expressions {#expressions}

Every well-formed ML expression \\(e\\)

-   has a type \\(t\\) written as \\(e : t\\)
-   may have a value \\(v\\) written as \\(e \Rightarrow v\\)
-   may have an effect (not for our effect-free fragment)


### Well-typed expressions with no values {#well-typed-expressions-with-no-values}

5 div 0 : int
This does not reduce to a value


### Notation Recap {#notation-recap}

e : t means e has type t
e \\(\Rightarrow\\) e' means e reduces to e'
e \\(\hookrightarrow\\) e' means e evaluates to e'
Reduce is one step, evaluate can be multiple
\\(\hookrightarrow\\) means the expression reduces all the way down to a value
A value is irreducible, will reduce to itself


### Extensional Equivalence {#extensional-equivalence}

Represented by \\(\cong\\)
Expressions are extensionally equivalent if they have the same type and one of the following is true:

-   They either both reduce to equivalent values
-   Both raise the equivalent exception
-   Both loop forever

21 + 21 \\(\cong\\) 42 \\(\cong\\) 6 \* 7
(fn x \\(\Rightarrow\\) x + x) \\(\cong\\) (fn y \\(\Rightarrow\\) 2 \* y)

Functions are extensionally equivalent if equivalent arguments map to equivalent results.


### Referentially Transparent {#referentially-transparent}

The value of an expression depends only on the values of its sub-expressions.
The type of an expression depends only on the types of its sub-expressions.


## 1/20 {#1-20}

Power function

```sml
(* power : int * int -> int
   REQUIRES: k >= 0
   ENSURES: power(n, k) -> nk
*)

fun power(_:int, 0:int): int = 1
  | power(n,k) = n*power(n, k-1);
```

power is not total as a negative k would loop forever.
Typing evaluation of if then else

if \\(e\_1\\) then \\(e\_2\\) else \\(e\_3\\) : t
if \\(e\_1\\): bool,
\\(e\_2\\) and \\(e\_3\\) are both t

Evaluation is left-to-right

```sml
fun power(n:int,0:int):int = 1
  | power(n,k) =
    if (even k)
    then square(power(n,k div 2))
    else n*power(n,k-1);
```

Prove correctness of code
Proof: By standard induction on k
Base Case: k = 0
NTS: power(n, 0) \\(\hookrightarrow n^0\\) for all values n : int

## 1/22 {#1-22}

A function si tail recursive if it is recursive and if it performs no computations after calling itself recursively.
Such recursive calls are said to be tail calls. (tail meaning at the end).

```sml
fun append ([]: int list, Y: int list) : int list = Y
  | append (x::xs, Y) = x::append(xs, Y);
```

Reverse a list efficiently with tail recursion

```sml
(*
trev: int list * int list -> int list
REQUIRES: true
ENSURES: trev(L,acc) = (rev L) @ acc
*)
fun trev ([]: int list, acc: int list) : int list = acc
  | trev (x::xs, acc) = trev(xs, x::acc);
```

trev([1,2,3,4],[]) =&gt; trev([2,3,4],[1]) =&gt; trev([3,4],[2,1]) and so on
